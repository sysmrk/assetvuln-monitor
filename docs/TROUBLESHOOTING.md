# V2 troubleshooting — first checks and safe fixes

This page is for **develop/v0.2** only. If you are using the future product's **V3**, go to the [V3 troubleshooting guide](https://github.com/sysmrk/assetvuln-monitor/blob/develop/v0.3/docs/TROUBLESHOOTING.md).

**Never delete a database volume as your first troubleshooting step.** Enter the affected V2 checkout and run:

~~~bash
git branch --show-current
docker compose ps
docker compose logs --tail=100 worker
docker compose logs --tail=100 metabase
~~~

The Git branch should be **develop/v0.2**. These checks are **read-only**.

## Installer refuses to start

### ".env missing" or "CHANGE_ME password"

V2 does not automatically generate passwords. First:

~~~bash
cp example.env .env
nano .env
~~~

If you already have a populated .env, **do not overwrite it with cp**. Replace all five placeholder passwords with independent values generated by:

~~~bash
openssl rand -hex 30
~~~

Repeat five times. Save in nano (**Ctrl+O**, Enter, **Ctrl+X**) and run:

~~~bash
chmod 600 .env
docker compose --profile setup config --quiet
./install.sh --demo
~~~

Use **--live** instead of --demo only when this is a **separate, new Live checkout** with real URL/token already configured.

If config validation still complains about a bootstrap-only credential, ensure the installer is the current V2 branch version; the V2 validation includes the **setup** Compose profile.

### Docker/Compose missing or inaccessible

~~~bash
docker --version
docker compose version
docker info --format '{{.ServerVersion}}'
~~~

If these fail, install/start Docker Engine or Docker Desktop and enable WSL integration. Do not reinstall an already running Docker Engine blindly; follow [prerequisites](INSTALLATION.md#0-prerequisites--start-here).

### Port 8444 already used

Open **.env**:

~~~bash
nano .env
~~~

Change both port settings to the same unused port, e.g.:

~~~dotenv
HTTPS_PORT=8454
PUBLIC_URL=https://localhost:8454
~~~

If this is an **additional V2 instance**, it also needs a **unique COMPOSE_PROJECT_NAME** before initial installation. Do not rename a populated Compose project to silence a port conflict.

### Browser warns about TLS

A self-signed **localhost** certificate is generated for Demo, so a local warning is expected. Use a trusted certificate before sharing access with a network or organization. Do not ignore warnings for untrusted remote hosts.

## Metabase problems

### The site opens but dashboards are missing

~~~bash
docker compose ps
docker compose logs --tail=100 worker
docker compose logs --tail=100 metabase
~~~

Once Worker schema initialization succeeds, rerun one-time bootstrap:

~~~bash
docker compose --profile setup run --rm bootstrap
~~~

Expected: log messages reporting provisioned dashboards. This changes **Metabase metadata**, not Endpoint Central devices. V2 should show **seven** dashboards.

### I forgot the initial login password

~~~bash
grep '^METABASE_ADMIN_EMAIL=' .env
grep '^METABASE_ADMIN_PASSWORD=' .env
~~~

This shows the **initial** values from your private V2 .env. If you changed the password in Metabase later, the stored initial value may no longer work. Follow the approved Metabase account-recovery flow; do not reset PostgreSQL.

## Live inventory and Findings

### Endpoint Central inventory is empty

Use the bundled, independent **GET-only** API test:

~~~bash
python3 scripts/test_manageengine_api.py
~~~

For an organization CA:

~~~bash
python3 scripts/test_manageengine_api.py --ca-bundle secrets/certs/org-ca.pem
~~~

Both **scanComputers** and **softwareInfo** should return **PASS**. If not, verify HTTPS URL, inventory token and certificate trust. A successful initial-page test does not guarantee full pagination works.

### Too many assets / pagination cap errors

Open **config/application.yaml** and set **manageengine.max_assets** above the real approved fleet size, starting from its protective default **10,000**. Only change **max_pages** after reviewing API behavior:

~~~bash
nano config/application.yaml
docker compose restart worker
~~~

A restart re-reads the inventory; avoid scheduling it repeatedly during business-critical hours.

### Assets appear, but no CVEs or Findings

This does **not** establish that the fleet is safe. Check:

1. Dashboard **03**: are software versions present?
2. Dashboard **07**: are approved software mappings still empty?
3. Run the read-only review queue:

~~~bash
docker compose exec -T worker python -m avm.review_cli list --status pending
~~~

4. Read [Mapping Review](MAPPING-REVIEW.md) and approve a **verified** identity.
5. Wait for the next inventory sync.
6. Check cve.now ingestion in Worker logs:

~~~bash
docker compose logs --tail=160 worker
~~~

V2 only queries a **bounded number of recent cve.now pages** and creates potential Findings from supported structured package/version evidence. Zero matches can reflect **missing mapping, limited coverage, stale inventory or actual absence of evidence**.

### An approval was ignored

The approval CLI changes **local database records**, but the Worker merges approved identities on its next successful inventory sync. Check Dashboard 07, the approval status and Worker logs. Repeating the approve command is not the appropriate fix.

## Data preservation

~~~bash
./scripts/backup.sh
docker compose stop
docker compose start
~~~

The backup script saves **AVM and Metabase PostgreSQL dumps only**. Store .env, certificates, application.yaml and token separately according to your security policy.

**Never use docker compose down -v as a troubleshooting shortcut**. The flag removes project volumes and can destroy your data. **scripts/restore.sh** is explicitly destructive and asks for confirmation; test with a verified backup in an isolated environment.

If you cannot resolve an error, capture a **redacted** log snippet, your V2 branch/Compose project name, and the failing command. Never share the raw .env, token, private key or database dump.
